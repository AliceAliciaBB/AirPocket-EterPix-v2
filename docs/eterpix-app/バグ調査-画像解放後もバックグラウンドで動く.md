# バグ調査: 「画像を解放」でホームに戻ってもバックグラウンドで動き続ける

調査日: 2026-11-07 / 状態: **調査のみ. 実装は別タスク完了後(未着手)**
修正計画: `計画.md` の「追加計画 X」(**承認済み 2026-11-07**. 実装は追加計画 W の完了後)
対象: `Assets/EterPixNudeNyang/Scripts/`(`NudeNyangEterPix.cs` / `EterPixAppImages.cs` / `EterPixAppFeed.cs`)

## 1. 報告(ユーザーの意図)
- 設定の「画像を解放」を押してホームに戻っても, アプリがバックグラウンドで動いている.
- 「画像を解放」はタスクキルの役割のはず. バックで動いていては意味がない. **kill できていない**.
- 期待: 解放してホームへ戻った時点で, 通信・取得・毎フレームの処理がすべて止まる(次に開くまで何もしない).

## 2. 計画書・要件との照合
- `計画.md`(W-4 / 追加計画付近)の記載: 「設定の『画像を解放』(`ReleaseAll`)でも破棄する」「取得済みの画像を全部捨て, アプリを閉じてホームへ戻る」.
- 計画は「**画像を捨てる + ホームへ戻る**」までで, 「**動作を止める**」とは書かれていない. 一方コードのコメントには「次に開くと起動画面になり, いまの位置の近くの画像だけ**取り直して**」とあり, 解放直後に取り直す設計になっている.
- つまりズレは **意図(完全停止) ↔ 計画書(捨ててホームへ, 停止の記載なし)** にある. 計画書の修正から始めるのが筋.

## 3. 現在の実装で動き続けるもの(コード読みによる原因. 実機での再現ログは未取得)

### 原因A(主因): 解放の直後に取り直しを始めている
`NudeNyangEterPix.cs:1472` `OnSettingsReleaseImages()`:
1. `images.ReleaseAll()` で画像を捨てる
2. `PlanResume()`(`:1487`)を呼ぶ → `images.BeginWindow / Want / EndWindow` → `EndWindow` が `StartNext()` を呼び, **`startupPreload`(既定3)枚のダウンロードが即座に始まる**
3. その後 `GoHome()` でホームへ

結果: ホームに戻った後も, 裏で3枚ぶんのダウンロード(5秒間隔)が走り, 解放したメモリがすぐ埋まり直す. これが「バックで動いている」の実体と思われる.

### 原因B: `GoHome()` は表示を切り替えるだけ
- `Present()`(`:236`)は `visible=false` で `panel.SetActive(false)` するだけ. スクリプトを載せた GameObject は有効のまま.
- `Update()`(`:263`)は非表示でも毎フレーム `SyncTick()` を回す(同期の送信, `pendingRemote` の適用待ち).
- `EterPixAppImages` の取得の連鎖(`OnImageLoadSuccess` → `Evict` → `StartNext`)と `EterPixAppFeed`(`:90` の `SendCustomEventDelayedSeconds` の再試行)は, 表示状態を見ずに続く.
- `OnDisable` は `CancelSwipe / HideDebug` だけ(`:578`)で, 取得も同期も止めない.

### 原因C: 取得中の1枚は止められない
`ReleaseAll()` は `_discardCurrent=true` で「届いたら捨てる」とするのみ. VRChat のダウンロードは取り消せないため, 解放後に最大1枚ぶんの通信は残る(捨てるので害は小さい. ただし完了までは動いている).

### 原因D(要確認): 本体シェルにタスクキル相当の関所が無い
- `NudeNyangTabletShell.cs` には `GoHome()`(`:569`)と最近使ったアプリの並び(`recent[]`)があるが, アプリを**終了させる**公開メソッドは見つからなかった(本体 `Assets/NudeNyang` は変更しない方針).
- したがって「kill」はアプリ側(`NudeNyangEterPix`)が自分で「停止状態」を持って実現するしかない.

## 4. 修正方針の案(承認を得てから実装. 別タスク完了待ち)
「**停止状態(killed)を1つ持ち, 全ての処理がそれを見る**」形にする.

1. 解放時は `PlanResume()` を呼ばない. 画像・HQ・取得待ち・取得中(届いたら捨てる)をすべて空にして, 新規ダウンロードを開始しない.
2. `killed` フラグを導入. `true` の間:
   - `Update()` の `SyncTick()` を止める(`pendingRemote` も破棄)
   - `EterPixAppImages` は `Want / EndWindow / StartNext` で何も開始しない
   - `EterPixAppFeed` の再試行(遅延呼び出し)を始めない
3. 次にアプリを開いた時(`Present` で `show` が false→true)に `killed=false` にして, 起動画面から `PlanResume()` 相当の取り直しを行う(いまの「push to start で続きから」は維持. 位置と気になるは残す)
4. 取得中の1枚だけは止められないので, 届いたら必ず捨てる(現状の `_discardCurrent` を維持)

### 見た目・挙動の変化(Step 4 の確認対象)
- 解放→ホーム→再度開く: 今は開いた時点で数枚が読み込み済みのことがあるが, 変更後は必ず読み込みから始まり, 起動画面の待ちが少し長くなる可能性がある. **ユーザーに見える挙動が変わるため, 実装前に承認が必要**.

## 5. 確認の進め方(実装時)
1. `[EtpTrace]` ログで検証(コンソールへ常時出す方針). 解放後に `img ... loaded` / `resume preload` / `visible=false` 以降の取得ログが**出なくなること**を確認
2. 解放 → ホーム → 5秒以上待つ → `[EtpTrace]` に新しいダウンロードの行が無いこと
3. 再度開く → 起動画面から取り直されること, 位置と気になるが残っていること

## 6. 未確認・注意
- ここまでは**コード読みのみ**. 実機(Play モード)で「裏で動いている」ことを `[EtpTrace]` で確認した記録は無い. 実装前に1回ログで再現を取るのが安全.
- 「バックで動いている」が具体的に何を指すか(通信, CPU, メモリ, 同期の送信)は, ユーザーに確認できていない. 上記は通信(ダウンロード)を最有力と推定したもの.
- 別セッションで進行中の作業(`feature/eterpix-copy-page`)と同じスクリプトを触るため, 着手はそちらの完了後.
